# MySQL 接入与实时分析方案

当前程序读取本地 DuckDB 成功快照，支持 CSV 接入；尚未实现 MySQL 连接器，也没有连接客户数据库。本文件是实施方案，示例不会自动执行。

## 接入链路

客户 MySQL（业务表或只读分析视图） → Python 采集程序 → 字段及指标核对 → 本地成功快照 → 看板自动刷新。

经营看板建议先以 30—60 秒为采集间隔。实际延迟是等待采集、查询、加工核对和页面刷新时间之和，不能把“每 60 秒刷新网页”等同于数据库已实时更新。需用客户实际数据量测量。

## 客户需要准备什么

1. MySQL 版本、服务器地址、端口（常用 3306）、库名，及运行程序的电脑可以访问它的网络条件。
2. 专用只读账号，尽量授权给指定分析视图或必要业务表。密码由客户填到本机配置，不放入源码、浏览器 URL 或聊天记录。
3. 订单、订单商品、客户、商品、支付、退款表的结构和关系；可以提供脱敏的 SHOW CREATE TABLE 输出，不需要实际客户个人信息。
4. 字段映射：唯一订单号、客户去重标识、购买日期、订单状态、客户省份、商品分类、商品金额、运费、支付金额。确认人民币、完成状态、退款、时间时区口径。
5. 数据量、峰值变化量、允许刷新延迟，以及是否能使用只读副本。

## 第一阶段：定时采集，复用现有核验链路

- 使用官方 MySQL Connector/Python 配置 host、port、user、password、database、连接/读写超时；远程连接按客户证书配置 TLS 证书与主机名校验。
- 首次做一致性读取，避免订单、商品和支付来自不同读取时点；商品与支付分别汇总再关联，防止金额被放大。
- 小数据量先做受控的全量快照，限制超时和并发；生产数据量增大后按更新标识增量同步。
- 轮询增量不能只靠下单时间；旧订单取消、退款、支付补记也会改变历史。若用 updated_at 水位，需有索引、稳定主键、重叠回看与主键幂等更新，处理同时间戳并列、迟到提交和删除，并定期全量对账。
- 没有可靠更新时间或删除标记时，不承诺轮询能完整捕获变化；改为定期全量或 CDC。
- 每批检查通过才发布新快照；失败保留旧版本，并显示“同步失败/数据延迟”。不把旧结果展示成已更新。
- 网页单独定时请求结果，显示最近一次成功同步时间、连接状态与“立即刷新”按钮。若一次采集耗时超过间隔，不并发叠加任务。

## 第二阶段：秒级变化采集

若确有秒级需求，使用 MySQL binlog → Debezium CDC → 分析存储 → 看板推送。首次一致性快照后持续读取 binlog，处理新增、修改、删除。需要客户 DBA 配置 binlog、采集权限、日志保留、断点恢复与监控；实际时延需压测，不能保证零延迟。

## 验收

- 用测试库修改一笔订单、取消旧订单、补支付、退款和删除记录，核对看板最终变化。
- 验证金额不因多商品、多支付关联而放大，客户数独立去重。
- 测试断网、超时、重复采集、重启恢复以及失败不发布。
- 测量提交到展示的实际延迟和业务库查询负载。
